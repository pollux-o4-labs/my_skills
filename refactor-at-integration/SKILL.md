# 통합 시점의 리팩토링

리팩토링은 외부 동작을 바꾸지 않으면서 내부 구조를 개선하는 작업이다. 통합 브랜치에서 수행한다.

이름 있는 기법만 쓴다. 기법·스멜·정정 대상·설계 원칙·테스트는 [CATALOG.md](CATALOG.md)가 정본이며, 스멜에서 커밋 분할까지의 경로는 [EXAMPLES.md](EXAMPLES.md)에 있다.

## Quick start

```
1 규모 판정      대형이면 좌석 소집, 소규모면 감독 직접
2 실측           안전망 없으면 착수 금지
3 스멜 식별      게이트 실행 → 통과해도 스멜은 따로 훑는다
4 기법 선택      스멜이 기법을 정한다 (CATALOG)
5 분할           대형만. 파일 소유로 나눈다
6 적용           리팩토링과 정정을 다른 커밋으로
7 검증           회귀 테스트로 등가성 단언
```

## 1. 규모 판정

공유 접합부·설계 원칙을 건드리면 대형, 국소 변경이면 소규모다.

| | 판정 주체 | 선행 조건 |
|---|---|---|
| 소규모 | 감독 직접 | 네 축을 순서대로 자기가 본다 |
| 대형 | 좌석 소집 | 계획 적대리뷰 통과 전에 구현자를 투입하지 않는다 |

판정 축은 상설 좌석과 같다. 새로 만들지 마라.

1. 문체 — 단독으로 먼저 돈다. 이 축만 파일을 고친다
2. 코드 — 정확성과 설계 품질
3. 방향 — 결정 기록·조문과의 정합
4. 고도 — 임시방편인가 근본인가. 과잉 방어도 같은 축이다

## 2. 착수 전 실측

저장소가 답하는 것을 사람에게 묻지 마라.

| 입력 | 확정 방법 |
|---|---|
| 안전망 | 대상 파일의 분기 커버리지. 전역 수치가 아니다 |
| 영향 범위 | 호출부·참조를 훑어 이름으로 적는다 |
| 우선순위 | 저장소가 선언한 원칙을 읽는다 |
| 종료 조건 | 반증 가능한 한 문장 |

유닛 테스트가 없으면 착수하지 마라. 첫 커밋이 특성화 테스트를 작성한다.

## 3. 스멜 식별

게이트를 먼저 돌린다. 기계는 분량·형식·색인·끊긴 참조만 재며 **통과는 정합의 증거가 아니다.**

카탈로그의 코드 스멜·문서 스멜로 훑는다. 정본 분열·혼재·산재·전재·사문은 뜻이라 기계가 판정하지 못하므로, 목록 검사를 신설하지 말고 좌석에 위임하라.

정정 대상이 같이 나온다. 분류만 하고 6에서 가른다.

## 4. 기법 선택

스멜이 기법을 정한다. 줄 수는 증상이고 원인은 SRP 위반이다.

문서는 압축이 선행한다. 분할 결과가 Deep Module이 아니면 실패다.

## 5. 분할 (대형만)

1. 교차 결정을 먼저, 혼자 — 이름·경계·공유 인터페이스
2. 관심사가 아니라 파일로 나눈다
3. 정합성 소유자를 지명한다

## 6. 적용

리팩토링과 정정을 같은 통과에서 발견하되 커밋을 나눈다. 재는 자가 다르다.

| | 대상 | 검증 기준 |
|---|---|---|
| 리팩토링 | 정본 분열 · 혼재 · 산재 · 전재 · 사문 | 뜻이 안 바뀌었나 |
| 정정 | 낡음 · 자기모순 · 못 지킬 약속 | 무엇이 바뀌었나 |

## 7. 검증

- 회귀 테스트로 등가성을 단언한다
- 반증을 먼저 시도한다
- 자기보고를 믿지 않는다. 감독이 직접 재현해 종료 코드로 판정한다
- 커밋 전 적대검증. 반려 사유가 재현되면 커밋하지 않는다
- 기각도 산출물이다

## 리팩토링이 아닌 것

기능 추가와 재작성은 리팩토링이 아니다. 그렇다고 말하고 진짜 작업을 하라.

가르는 기준은 종료 조건이다. 새 동작을 말하지 않고는 못 쓴다면 리팩토링이 아니다.

무엇을 고칠지 **찾는** 단계는 `improve-codebase-architecture`가 맡는다.
