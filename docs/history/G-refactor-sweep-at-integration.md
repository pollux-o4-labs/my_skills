# G — 통합 시점 병렬 리팩토링 스윕

> **BLUF:** 통합 브랜치에 기능 PR이 쌓인 뒤 영역 분할 병렬 분석을 돌려 17건 중 5건만 채택하고 12건을 근거와 함께 기각한 실측 — 기각이 산출물이라는 점이 핵심.

## 상황

ai-harness 저장소에서 통합 브랜치(`integ/shared-rules`)에 기능 PR 두 건이 머지된 뒤,
main으로 올리기 전에 리팩토링 여지를 물었다.

코드는 총 2,875줄(9개 모듈)이었고, 분석자 3명에게 영역을 나눠 맡겼다.

- 게이트 판정 코어 2파일(1,796줄)
- 생성기·설치기 5파일(~800줄)
- 설정·배선·의존 그래프

## 실측

- 제안 17건 중 **채택 5건, 기각 12건**.
- 분석자 2명이 **독립적으로 같은 순환 참조**를 지목했고, 한쪽이 결정적 근거를 댔다 —
  문제의 두 함수가 자기 파일 안에서는 호출 0건이라 순환의 원인이 "필요해서"가
  아니라 "안 옮겨서"였다.
- 한 분석자가 코드 주석의 근거가 **사실과 다름**을 짚었다 — "외부 의존 제약 때문에
  합칠 수 없다"고 적혀 있었으나, 이미 제3의 공유 모듈이 존재해 그 이유가 성립하지 않았다.
- 성능 의심 지점은 실측 결과 **낭비 없음**으로 판정됐다(정규식 내부 캐시·프로세스당 1회 실행).
- 매 커밋 훅에서 도는 경로에서만 실제 중복 I/O가 확인됐다(디렉터리당 하위 프로세스 2회).

## 무엇이 이 결과를 만들었나

- **영역 분할**(관점 분할이 아니라) — 같은 파일에 여러 관점을 얹으면 같은 발견이
  세 번 돌아오고, 영역을 나누면 커버리지가 나온다.
- **프로젝트 제약을 그대로 주입** — 이걸 안 주면 이 프로젝트가 받을 수 없는
  외부 라이브러리 제안이 쏟아진다.
- **"고칠 게 없으면 없다고 말하라"를 명시** — 이 허가가 없으면 분석자는 쓸모 있어
  보이려고 제안을 지어낸다.
- **기존 주석을 설계 근거로 읽고 수용하거나 반박하라** — 주석 오류가 여기서 나왔다.
- **등급 강제**(지금/나중/하지마) — 등급이 없으면 감독이 17건을 다시 분류해야 한다.
